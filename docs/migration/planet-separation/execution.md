| Вариант | Что выигрываем | Что остаётся нерешённым | Решение |
|---|---|---|---|

Сначала проверить эту гипотезу на Flights |
| Продолжать добавлять специальные адаптеры по одному | Быстро появляется ещё одна функция на Navara | Текущий switch продолжает уничтожать приложение, данные и живые инструменты | Использовать точечные адаптеры в графике; владение состоянием изменить до массового переноса |

**Темп.** После пилота записать фактическую трудоёмкость малой, средней и сложной строки. Для сложной строки учитывать повторное ревью и измерения. Оценку оставшихся волн получать из числа адаптеров соответствующего типа и совместно используемых операций. Не переносить исторические оценки Dioxus на текущую Vue-ветку. Графические spikes по drape, video projection и wind допускаются после контракта их входов; включение общей смены находится на критическом пути после надёжного handoff.

## Что делает комплект пригодным к продолжению

У одного изменения есть исполнитель, проверяющий и журнал доказательств; это роли процесса, запуск субагентов не требуется. Исполнитель берёт ID слоя или системный пакет, фиксирует входные зависимости, обновляет строку результата и коммитит локально. Проверяющий повторяет те же fixtures на двух планетах. Для каждой выявленной разницы выбрать одно из трёх действий: исправить, сохранить намеренное визуальное отличие с эталоном, отложить с видимым ограничением. Последний вариант допускает продолжение других пакетов, но блокирует финальный статус паритета этой функции.

**Пример движения одного бага.** У выбранного `71be26` во время переключения приходит новая позиция. Модель повышает ревизию с 814 до 815. Навигация держит ключ рейса и режим cockpit. Кандидат восстанавливает позу по состоянию на 815. Обработчик клика старой сцены отключается при передаче управления; поздний GLB ревизии подключения старой сцены уничтожается. Ни URL, ни повторный запрос OpenSky не участвуют. Тест фиксирует ID, текущую позицию с допуском маршрута, отсутствие пропущенного события и сохранение работы после возврата.

## Как воспроизвести проверку охвата

Снимок файлов привязан к базовому коммиту. Сравнить первую колонку files.tsv (без заголовка) с отсортированным выводом `git ls-tree -r --name-only 9aaa6348`. Для слоёв сравнить ID с `APPLICATION_LAYER_DIRECTORY`, для Navara — с ключами `loaders` в `src/app/navaraMode.js`. Для interfaces.tsv сверить имена отдельно внутри каждого вида с `package.json#exports`, `scripts/package-boundaries.json`, `GEV_ACTION_SCHEMAS`, `coreTools` и `src/maps/catalog.js`. Совпадение имён между голосом и запросом допускается; индексируется пара «вид, имя».

Путь в files.tsv указывает назначение работ и начальную проверку, но не является аудитом каждой строки программы. Прямые SDK imports выделены статическим поиском; динамические зависимости, глобальные объекты и вызовы через services нужно подтвердить при переносе поведения. В parity.tsv содержится краткий идентификатор из исторического описания; полный контекст доступен по имени файла и номеру строки в каталоге `gev-navara/plans/parity-parts`. Все новые функции после базового коммита требуют новой строки или явно названного существующего теста.
